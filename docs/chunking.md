# Создание и проверка чанков — текущее состояние 10.10.2026

Текущий pipeline обрабатывает зарегистрированные immutable PDF/DOCX: scripts.parse_registered_corpus → scripts.index_corpus. Активны 3664 чанка 18 документов (15 public, 2 договора, 1 закрытый synthetic OCR fixture). Первые 842 chunks ниже — исторический предварительный Unicode baseline, не действующий индекс.

Используется настоящий tokenizer выбранного E5 (480 tokens, overlap 16), ONNX CPU embeddings, immutable PG spans и проверяемые Qdrant generations. PDF: pypdf + Hebrew OCR при плохом text layer; таблицы pdfplumber точно связываются с диапазонами, ambiguous cells требуют review. DOCX: безопасный OOXML v2, paragraph/table/row/cell и numbering/style inheritance; physical PDF pages не выдумываются. OCR confidence ≥80; bbox хранится для OCR lines и однозначных table cells. printed_page_number не определён автоматически. Сложная структура, header/footer/footnote context и все Hebrew locators требуют ручной QA; synthetic tests её не заменяют.

Адаптер юридических снимков реализован в app/retrieval/legal_index.py: только reviewed verified chain, exact clause spans и provenance, повторная проверка перед ответом. Реальные цепочки пока отсутствуют. Поиск по raw закону как действующей норме заблокирован.

Команды: docker compose run --rm --no-deps --user root api python -m scripts.parse_registered_corpus; затем scripts.index_corpus. Первичный create_chunks --store оставлен для воспроизводимости public baseline. Полный статус и доказательства: docs/progress.md. Backup сохраняет registered/chunks JSON в pipeline.tar.gz; повторная индексация по PG не требует старого chunks manifest.

## Исторический предварительный pipeline

# Создание и проверка чанков

Реализован локальный административный pipeline для 15 сохранённых PDF. Он проверяет SHA-256 оригинала, извлекает текст каждой страницы через pypdf 5.9.0, сохраняет исходные блоки и создаёт структурные чанки. Закон из raw PDF в этот pipeline не допускается: для него нужен отдельный адаптер проверенных снимков legal engine.

## Запуск

Из корня проекта в PowerShell:

```powershell
docker compose build api
docker compose run --rm --no-deps -v "${PWD}:/source" -w /source api /workspace/.venv/bin/alembic upgrade head
docker compose run --rm --no-deps --user root -v "${PWD}:/source" -w /source api /workspace/.venv/bin/python -m scripts.create_chunks --store
```

Для проверки без PostgreSQL можно выполнить `python -m scripts.create_chunks` в имеющейся среде с pypdf 5.9.0. Для отдельного повторного импорта: `python -m scripts.chunk_registry` в Docker. Артефакты и manifest находятся в `data/chunks/`, исходники не изменяются. Повторный запуск с теми же параметрами сохраняет те же IDs и hashes. JSON каждого результата неизменяем; manifest выбирает текущий набор. Промежуточные JSON первых проверочных запусков остаются локально для воспроизведения исправлений и не включены в текущий manifest или поисковый индекс.

## Правила и точность

- Пункты и подпункты распознаются по осторожным правилам нумерации; даты и номера сносок без точки не создают новый пункт. Неподтверждённые границы имеют medium/low confidence.
- Продолжение пункта на следующей странице сохраняется в той же группе; новый распознанный пункт открывает другую группу. Маленькие соседние пункты не склеиваются для заполнения лимита.
- Большой пункт делится на parts. Overlap разрешён только внутри этого пункта; точные исходные диапазоны позволяют позже объединить пересекающиеся цитаты без повторения.
- Повторяющиеся контактные колонтитулы сохраняются в оригинальных блоках и исключаются из поискового текста. Четыре декоративные/пустые страницы отдельно подтверждены визуальным просмотром и записаны в config/chunking.json.
- Каждый span указывает block_id, диапазон символов оригинального блока и диапазон в чанке, страницу PDF от 0 и displayed_page от 1. Диапазоны измеряются Unicode-символами Python, не UTF-8 байтами. printed_page_number и bbox пока null; номер PDF не выдаётся за напечатанный номер.
- Нормализация identity-v1: исходный извлечённый текст сохраняется; между блоками для поиска добавляется только перенос строки. Все содержательные символы чанка должны иметь исходный span. Проверяется покрытие всего пригодного извлечённого текста и сохранение исключённых блоков.
- parsing_revision, chunk_id и fingerprints детерминированы. PostgreSQL содержит parsing_revisions, blocks и chunks; UPDATE исходных диапазонов запрещён. Повтор импорта не создаёт дубликаты. Изменённая конфигурация разбиения создаёт другие чанки с теми же исходными блоками.

## Результат 09.10.2026

15 PDF, 205 страниц: 201 страница с текстом и 4 просмотренные страницы без содержательного текста. Созданы 1262 исходных блока и 842 чанка. Проверки исходных диапазонов, hashes, покрытия и лимитов прошли. Исправлены ошибочное распознавание сносок и попадание контактного колонтитула в чанки. Промежуточные 849 неактивных чанков заменены в PostgreSQL исправленным набором в одной транзакции с audit; оригиналы не затронуты.

## Границы реализации

Все чанки имеют quality_status=staged_unreviewed, index_generation_id=null и current_norms_eligible=false. Юридические статусы документа сохраняются отдельно; при будущем поиске они проверяются в реестре, а не принимаются из устаревшего payload. Векторный индекс не создан и не активирован.

Tokenizer unicode-word-punctuation-v1 считает Unicode-слова и знаки препинания, лимиты 800/100. Это временный tokenizer для структурного разбиения. Он не гарантирует лимит ещё не выбранной embedding-модели: T05 обязан пересчитать размер её tokenizer и при необходимости пересоздать чанки до индексации.

Текстовый слой PDF не доказывает правильность порядка таблиц и боковых примечаний. Ячейки таблиц, bbox, heading styles и разделение сносок пока не восстановлены; предупреждения сохраняются в каждом артефакте. Визуально сверены примеры определения стандарта 21.1 и пункта 1.20 типового договора. Это выборочная проверка, а не постраничная проверка содержания всех PDF. DOCX, OCR he, поколения индекса и chunk adapter юридических снимков остаются последующими частями T03/T04. При появлении слабого текстового слоя страница получает ocr_required, её текст не попадает в чанки; автоматического OCR ещё нет.
