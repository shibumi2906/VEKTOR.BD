# Механизм актуальности законов

Реализован самостоятельный срез T11 по прямому поручению пользователя: учёт нормализованных поправок, сборка редакции на дату и обязательный контроль перед поиском. Это не завершение parser, Qdrant/LLM и HTTP query pipeline.

## Данные и проверка

Контракт `app/models/legal.py`: LawChain содержит закон, исходные пункты, поправки и ChainReview. Каждая поправка адресует пункт, хранит операцию replace/delete/insert_after/repeal_law, hash ожидаемого текста, дату/срок действия, источник и условия. Один официальный акт с несколькими сроками/режимами нужно разложить на отдельные однозначно упорядоченные записи. `conditions` — AND; `any_conditions` — OR групп AND. Поддержаны сравнения ISO дат/целых чисел и равенство строк/boolean. Неизвестные или некорректные факты не угадываются.

Проверяющий должен подтвердить исходный текст, точную расшифровку операций, весь перечень изменений и условия по официальным источникам. `complete=true` и `verified` — результат этой работы, не автоматическое доказательство. Репозиторий допускает URL только зарегистрированных official sources. Полнота автоматическим обходом сайта Кнессета и автоматическое извлечение правовых инструкций из PDF пока не реализованы. Не поддержанные сложные положения нельзя упрощать молча: они остаются manual_review.

ChainReview хранит expected_amendment_ids (включая уже включённые в baseline IDs), covered_from/checked_through, checked_at/next_check_at с timezone, reviewed_by и доказательство перечня. Baseline должен соответствовать своей baseline_effective_from; более ранние поправки помечаются включёнными в него и не применяются повторно.

## Выполнение

`compile_law` выбирает изменения на as_of, по умолчанию дата обращения определяется в Asia/Jerusalem. SHA-256 перед изменением проверяется по точному тексту, без скрытой нормализации. Временные изменения действуют до effective_to, не включая эту дату. Если сочетание временных/постоянных изменений не совпадает с ожидаемыми промежуточными текстами, возвращается version_conflict, а не предположение об актуальной норме. Отмена закона не отдаёт действующий текст.

Неполная цепочка, неизвестные даты, просроченная проверка, неподтверждённый исходник, неясные переходные условия и конфликт текста возвращают статус и **пустые clauses**. Только verified сохраняется в legal_snapshots. Неизменяемый fingerprint включает цепочку, дату, факты, результат и compiler_revision. Происхождение каждого пункта включает первоисточник/поправки; результат is_derived_text=true нельзя выдавать за дословную цитату единого официального PDF.

PostgreSQL: legal_laws, legal_chains, legal_amendments, legal_snapshots; миграции 0002_legal_chains и 0003_legal_gate. Выбор новой цепочки аудируется; повторный импорт одинаковой цепочки идемпотентен. Указатель current_chain принадлежит тому же закону. Сохранённые цепочки/поправки/снимки нельзя перезаписывать.

В registry.document_register законодательные категории имеют legal_engine_required=true и не попадают напрямую в current_norms_eligible. Это закрывает обход через простые флаги у PDF. Стандарт/иные документы продолжают отдельную проверку по статусам/датам; наличие одной подтверждённой нормы не подтверждает весь корпус.

## Поисковый контракт

`retrieve_current_legal_evidence` сначала подтверждает **все** запрошенные законы, затем вызывает переданный поисковый адаптер. Scope содержит точные snapshots. Hit передаёт law_slug, clause_id, snapshot_sha256, start/end и text_he. Старый snapshot, чужой закон, неверный span или отличающийся текст вызывают LEGAL_EVIDENCE_MISMATCH. Пустые результаты — INSUFFICIENT_EVIDENCE. После поиска выполняется повторная проверка; перед выдачей сгенерированного ответа query pipeline обязан вызвать revalidate_legal_scope ещё раз. Изменение цепочки — SOURCE_CHANGED.

Векторный адаптер должен индексировать производные пункты и фильтровать по snapshot_sha256; он ещё не реализован. Локальный query pipeline и генерация также pending. Функции не используют тестовый поиск вместо настоящего Qdrant.

## Локальные административные команды

Запущен PostgreSQL проекта. Выполнять из корня:

```powershell
docker compose run --rm --no-deps -v "${PWD}:/source" -w /source api /workspace/.venv/bin/alembic upgrade head
docker compose run --rm --no-deps -v "${PWD}:/source" -w /source api /workspace/.venv/bin/python -m scripts.legal_registry seed
docker compose run --rm --no-deps -v "${PWD}:/source" -w /source api /workspace/.venv/bin/python -m scripts.legal_registry status
docker compose run --rm --no-deps -v "${PWD}:/source" -w /source api /workspace/.venv/bin/python -m scripts.legal_registry import --input data/reviewed-chain.json
docker compose run --rm --no-deps -v "${PWD}:/source" -w /source api /workspace/.venv/bin/python -m scripts.legal_registry resolve --law pinui --as-of 2026-10-09
```

Для import нужен действительно проверенный JSON по LawChain, не учебный пример. Факты передаются `--facts data/query-facts.json`; тексты/факты не печатать в обычные production logs. Ввод цепочек остаётся локальным CLI с документальной проверкой. Query/Qdrant/answer используют этот gate и exact snapshot provenance; синтетическая интеграция проверена с rollback, реальные цепочки отсутствуют. Личный UI работает без входа.

## Состояние реального корпуса

16 законов зарегистрированы без проверенных цепочек; реальные правовые редакции не выдуманы. Pinui возвращает chain_incomplete и пустой текст. Остались 15 PDF (205 страниц), 18 gaps; поправки и старые PDF не восстановлены. Нормализованные выдержки и ссылки служат техническими доказательствами сборки; пользовательский нормативный корпус должен показывать одну подтверждённую рабочую редакцию. Исторические снимки — внутренние записи воспроизводимости, не самостоятельные действующие варианты.

Тесты используют только синтетические нормы и rollback PostgreSQL; тестовые источники/цепочки не остаются в production registry. Связи требований: REQ-SRC-05–08, REQ-DATA-01, REQ-SRC-01/02, REQ-EXT-52-09/10.
