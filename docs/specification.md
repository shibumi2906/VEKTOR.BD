# Техническая спецификация PinuiRAG

Многоязычный сервис поиска по документам на иврите

Версия 1.6 • 10 октября 2026 • Реализация в Codex

Этот документ задаёт требования к одному законченному сервису для работы с корпусом פינוי־בינוי. Сервис работает с корпусом на иврите и отвечает на языке обращения по найденным источникам, подтверждает утверждения цитатами, сохраняет редакции и сравнивает конкретные темы в договорах. План T01–T14 охватывает весь результат. Тематическое сравнение договоров и автоматическое обновление корпуса сохраняются в плане. Предусмотрены режим ответа с LLM и режим поиска на иврите без внешнего API-ключа. Проект рассчитан на 1–2 пользователей и демонстрацию работы векторной БД.

Для Codex Markdown-версия сохраняется как docs/specification.md. Разделы 1–50 описывают продукт и технические требования; 51–58 задают контракты, схему, проверки и рабочую последовательность. Требования с REQ IDs обязательны. Стартовые настройки допускают изменение по измерениям с фиксацией решения; выбранные модели, источники и целевые показатели закрываются на указанных этапах до финальной приёмки.

Изменение 1.6 по решению пользователя: приложение используется на личном компьютере, без посторонних. Режим AUTH_MODE=local; вход, токены и выбор роли в UI отсутствуют. Все локальные документы и операции доступны владельцу компьютера. Порты опубликованы только на loopback; чужие Host/Origin отклоняются. Прежние требования admin/reader/grants относятся только к сохранённому опциональному token-режиму и не являются условием приёмки личного режима. Секреты модели, источники, точные цитаты, бюджеты и проверки актуальности остаются обязательными.

Содержание изменений версии 1.5: порядок работ C01 (скачивание официальных документов) → T02–T07 (БД и индекс) → T08–T10 (вопросы и тематическое сравнение) → T12–T13 (интерфейс); T11 проверяет актуальность и обновления уже скачанного корпуса. API-ключ не блокирует подготовку БД. Содержание изменений версии 1.4: добавлены стабильные IDs ненумерованным положениям, явный bootstrap T01 и использование существующих runtime (ADR-001). Сохранённые изменения версии 1.3: оставлено только тематическое сравнение договоров; исключены полное сравнение, выравнивание всех блоков и связанные jobs, API, бюджеты и критерии приёмки. Сохранены изменения версии 1.2: корпус на иврите, многоязычные вопросы и ответы, локальные embeddings и поиск без API-ключа.

## 1 Назначение и цель системы

REQ-EXT-01-01. Разработать сервис для 1–2 пользователей с документной базой на иврите. Сервис принимает вопросы на поддерживаемых языках, переводит их на иврит для поиска и отвечает на языке обращения, подтверждает существенные утверждения цитатами и указывает документ, редакцию и locator. Он поддерживает отдельные редакции, сравнение договоров, автоматическое пополнение и обновление корпуса.

REQ-EXT-01-02. Рабочий поток с LLM: вопрос → определение языка ответа → разрешение документа и области поиска → перевод вопроса на иврит (пропустить для he) → локальные embeddings и hybrid retrieval на иврите → локальный reranker → evidence context на иврите → LLM → проверка claims → ответ на языке обращения с citations. Без API-ключа: вопрос на иврите → тот же локальный поиск → оригинальные фрагменты и ссылки; связный ответ не генерируется. Фактическим источником является база документов; общие знания LLM не заменяют доказательства.

## 2 Предметная область

REQ-EXT-02-01. Язык всех индексируемых документов — иврит (language=he); отдельные иностранные имена и термины внутри оригинала допустимы. Переводы для UI не индексируются как самостоятельные источники. Начальный корпус относится к פינוי־בינוי и городскому обновлению в Израиле. В него входят законодательство, подзаконные и нормативные акты, официальные инструкции, материалы הרשות הממשלתית להתחדשות עירונית, права собственников и обязанности застройщиков, представители собственников, отказавшиеся и пожилые собственники.

REQ-EXT-02-02. Также обязательны תקן 21 и актуальные связанные оценочные стандарты, работа оценщиков и назначение שמאי פינוי בינוי, оценка экономической целесообразности, планирование и строительство, релевантные налоговые нормы и официальные методические документы. Договорный корпус включает типовые и реальные договоры и разные редакции одного договора.

REQ-EXT-02-03. Техническая архитектура позволяет добавить другие предметные категории без изменения retrieval pipeline. Первичное покрытие корпуса фиксируется manifest на C01; подтверждение действующих редакций и полнота проверяются на T11, а не объявляются по числу файлов.

## 3 Требования к источникам и актуальности

REQ-SRC-01. Законодательство, нормативы, стандарты и официальные инструкции включаются в актуальный поиск только в подтверждённой действующей редакции. Более поздняя дата публикации сама по себе не доказывает вступление в силу. Сохранять publication_date, effective_from, effective_to, checked_at, источник подтверждения и историю проверки; неизвестные даты оставлять null.

REQ-SRC-05. Связывать каждую нормализованную поправку с законом и адресуемым пунктом: операция, SHA-256 ожидаемого предыдущего текста, новый текст на иврите, порядок, даты действия, условия применения и официальный источник с URL, автором, SHA-256 и страницей/пунктом. Операции replace/delete/insert_after/repeal_law выполняются детерминированно по проверенным данным; естественный язык PDF или вывод LLM не является исполняемой поправкой. Один акт с разными датами/условиями разбивается на явно проверенные нормализованные записи.

REQ-SRC-06. Перед сборкой проверять полный перечень нормализованных изменений по официальной истории закона, статус проверки исходного текста и каждой поправки, покрытие даты as_of, checked_at/next_check_at и подтверждение проверяющего. Само совпадение IDs не доказывает полноту: complete/verified устанавливаются по документальной проверке. При неизвестной дате, неполной цепочке, устаревшей проверке или несовпадении ожидаемого текста возвращать отказ в подтверждении актуальности без частично собранного нормативного текста.

REQ-SRC-07. Собирать текст на as_of с учётом вступления в силу, исключительной верхней границы срока действия, отмены закона и переходных условий AND/OR по явно заданным фактам. Если применимость зависит от неизвестных фактов, вернуть applicability_unknown и список недостающих полей. Для каждого действующего пункта сохранять происхождение и IDs применённых изменений; редакция имеет неизменяемый SHA-256, зависит от даты/фактов/цепочки/версии компилятора и маркируется как производный текст, а не официальный оригинал.

REQ-SRC-08. Retrieval по законам допускается только через проверенный набор редакций: полностью подтверждены все запрошенные законы, поисковый адаптер ограничен выбранными snapshot SHA-256, каждый возвращённый span совпадает с текущим пунктом. Не запускать retrieval/LLM при неполной цепочке. Повторно проверять набор после поиска и перед выдачей ответа; новая цепочка или просроченная проверка блокируют старый результат. Флаги verified/current у исходного PDF сами по себе не дают доступ к current_norms для закона.

REQ-EXT-03-01. version_status: current | superseded | historical | unknown. Это статус редакции внутри семейства.

REQ-EXT-03-02. legal_status: in_force | repealed | not_yet_effective | unknown | not_applicable. Это применимость нормативного документа.

REQ-EXT-03-03. document_role: official | draft_contract | signed_contract | contract | template | reference. contract означает реальный договор без подтверждения подписания. Наличие файла не доказывает подпись.

REQ-EXT-03-04. verification_status: pending | verified | stale | failed | manual_review. Ошибка проверки не означает отмену документа.

REQ-EXT-03-05. ingestion_status определён отдельно в разделе 17. Универсальное поле status в документе и document_status в payload не использовать.

REQ-SRC-02. В режиме current_norms допускать только version_status=current, legal_status=in_force, verification_status=verified, effective_from <= as_of и effective_to > as_of либо null. По умолчанию as_of — сегодняшняя дата Asia/Jerusalem. unknown не трактовать как действующую норму.

REQ-EXT-03-06. Если даты действия подтверждены и документ действует бессрочно, effective_to=null. Если начало действия неизвестно, исключить документ из current_norms и направить на ручную проверку. Исторический поиск осуществляется по отдельному режиму historical, без автоматического применения старой нормы к текущей ситуации.

REQ-SRC-03. До загрузки полного корпуса заполнить config/sources.yaml реальными официальными URL и правилами проверки. На этапе разработки допустимы только синтетические источники в тестах. Запись содержит source_id, название органа, allowed_hosts, allowed_path_prefixes, документные категории, check_interval_seconds, метод проверки и правила разрешённых редиректов.

REQ-EXT-03-07. Нормативный документ нельзя активировать до проверки источника и редакции. Публикации СМИ, юридических блогов и агрегаторов могут быть reference, но не заменяют подтверждение официального текста. Если консолидированной редакции нет, комплект основного акта и поправок остаётся manual_review до подтверждения полноты.

REQ-SRC-04. После bootstrap T01 выполнить C01: скачать официальные тексты законов и связанные документы на иврите, сохранить URL, SHA-256 и manifest с пробелами покрытия. По решению пользователя от 09.10.2026 нормативный корпус хранит один полный подтверждённый действующий текст каждого закона/документа; отдельные поправки, исправления и предыдущие варианты удаляются из БД и хранилищ по явному административному поручению. Полный текст закона должен включать вступившие в силу изменения на дату проверки; исходная публикация или последняя поправка его не заменяют. При отсутствии подтверждённого сводного текста фиксировать gap, не объявлять старый текст действующим. Дополнительные рекомендации и шаблоны остаются отдельными документами с собственной проверкой; отсутствие замены в поиске само по себе не подтверждает их актуальность. После поручения реализовать учёт поправок нормализованные изменения пунктов и доказательства их применения сохраняются технически по REQ-SRC-05–08; удалённые исторические PDF не восстанавливаются автоматически. Проектные договоры 04.2025/08.2025 остаются доступны для тематического сравнения; это правило очистки относится к общему нормативному корпусу. Затем T02–T07 создают БД и индекс, T08–T10 реализуют ответы и сравнение, T12–T13 — интерфейс. Загрузка сама по себе не подтверждает действующую сводную редакцию.

Стандарт 21.1 (תקן 21.1) обязателен в корпусе проекта. Требуется полный утверждённый текст, а не проект или краткое изложение; сохранить редакцию, источник публикации и SHA-256. Проверку его актуальности выполнять по REQ-SRC-01/02.

Связанные официальные документы о минимальной прибыли застройщика и оплате организаторов сохранять отдельно от базового стандарта, с собственными датами и условиями применимости. Переходные правила стандарта и дополнений учитывать при выборе источников; позднейший документ не применять автоматически к договорам 2025 года.

## 4 Сбор и повторная проверка документов

REQ-ING-01. acquisition поддерживает автоматическую загрузку из source_registry и ручную загрузку PDF/DOCX администратором. Для загрузки необходимы title, document_type, category, language=he, document_family_id, document_role и область доступа. project_id=null допустим для общедоступного нормативного корпуса.

REQ-EXT-04-01. source_registry хранит source_id, source_type, source_url, check_interval_seconds, last_successful_check, next_check_at, verification_status, ETag и Last-Modified, если источник их предоставляет. source_type: official | manual | reference. Ошибки и результаты каждой проверки сохраняются в source_checks.

REQ-EXT-04-02. Планировщик создаёт задания проверки в PostgreSQL; worker выполняет загрузку с timeout, ограничением размера и повторными попытками. Интервал по умолчанию 86400 секунд является рабочей настройкой, а не гарантией ежедневного появления актуальной редакции.

REQ-EXT-04-03. Неизменившийся hash обновляет дату успешной проверки без повторного parsing. Изменение файла создаёт новую неизменяемую редакцию. Даже одинаковый извлечённый текст при изменении исходных байтов создаёт новый document_id, чтобы сохранить точный источник цитат; повторные embeddings можно переиспользовать по fingerprint.

REQ-EXT-04-04. Новая нормативная редакция проходит parsing, проверку полноты, indexing и подтверждение действительности. Только после этого переключается current_document_id. При ошибке старая готовая редакция сохраняется, но при истечении срока проверки перестаёт участвовать в current_norms.

REQ-EXT-04-05. Ручное подтверждение фиксирует actor_id, время, основание и evidence_url. LLM может предлагать метаданные, но не подтверждает юридическую актуальность автоматически.

## 5 Реестр документов и идентификаторы

REQ-DATA-01. PostgreSQL — источник истины для документов, доступа, редакций, блоков, chunks, заданий и результатов сравнения. Qdrant — производный поисковый индекс; его payload не является окончательным источником актуальности и прав доступа.

REQ-EXT-05-01. Иерархия: project → document_family → document_version → block → chunk. Для общих нормативных документов project_id=null. Один document_family относится к одному проекту либо к общему корпусу.

REQ-EXT-05-02. document_id идентифицирует конкретную неизменяемую редакцию и является UUID. Отдельного version_id для той же сущности не вводить. document_family_id — UUID семейства; version_label — человекочитаемое обозначение, не ключ. Числа в заголовках и датах не использовать как ID.

REQ-EXT-05-03. Примеры contract_shapira_hagag_2025_04 и contract_shapira_hagag_2025_08 в документе обозначают aliases, а не UUID API. Alias разрешается в document_id внутри конкретного проекта и семейства.

REQ-EXT-05-04. Минимальная запись редакции: document_id, document_family_id, project_id, title, title_he, title_ru, document_type, category, language, version_label, document_role, version_status, legal_status, verification_status, ingestion_status, publication_date, effective_from, effective_to, source_id, source_url, source_name, raw_file_key, file_sha256, checked_at, indexed_at, created_at.

REQ-EXT-05-05. Даты календаря хранятся как date, события — timestamptz в UTC. SHA-256 записывается hex строкой длиной 64. Исходные файлы неизменяемы и хранятся в закрытом Docker volume; путь файловой системы не возвращать клиенту. Скачивание оригинала — через авторизованный endpoint.

REQ-EXT-05-06. Схема, ограничения и индексы создаются миграциями Alembic. Полный состав сущностей и транзакционные ограничения — раздел 52.

## 6 Версионность и разрешение названий

REQ-VER-01. document_family связывает редакции и содержит nullable current_document_id. Указатель current обозначает выбранную рабочую редакцию семейства; для договоров он не утверждает, что договор подписан или юридически действителен.

REQ-EXT-06-01. Фикстуры Shapira Hagag: 04.2025 имеет document_role=draft_contract; 08.2025 имеет document_role=contract до отдельного подтверждения подписи. Подтверждённое подписание переводит роль в signed_contract с записью основания в audit_events.

REQ-EXT-06-02. version_status апрельской и августовской редакций определяется выбранной рабочей редакцией, а не словом «проект». Обе редакции остаются доступны при явном выборе, сравнении или историческом режиме.

REQ-EXT-06-03. В document_aliases регистрируются «04.2025», «апрельский договор», «проект договора», «08.2025», «августовский договор», «реальный договор». Уникальность alias проверяется в области проекта и семейства, а не по всему корпусу.

REQ-VER-02. При нескольких совпадениях resolver возвращает clarification_required с кандидатами и не запускает retrieval. Явный document_id имеет приоритет; противоречие между ним и названием в вопросе возвращает 422 FILTER_CONFLICT.

REQ-EXT-06-04. Нельзя считать последнюю дату в названии автоматически актуальной редакцией. Выбор current и подтверждение актуальности являются отдельными операциями реестра.

## 7 Поддерживаемые форматы

REQ-EXT-07-01. Обязательны PDF и DOCX, включая PDF со сканированными страницами. Parser Protocol должен позволять добавить HTML, XLSX и TXT без изменения retrieval-архитектуры. Их реализация не входит в обязательную приёмку текущего сервиса.

## 8 Извлечение текста и адресация блоков

REQ-PARSE-01. PDF сначала обрабатывается по текстовому слою; OCR включается постранично при отсутствующем либо непригодном слое. OCR должен поддерживать he; поддержка других языков не обязательна. Parser сохраняет последовательность блоков, заголовки, таблицы и bbox, если доступны. Качество OCR фиксируется отдельно; непригодная страница не считается успешно обработанной.

REQ-EXT-08-01. DOCX обрабатывается в порядке XML: paragraphs и tables, styles, numbering, lists и вложенные таблицы. Нельзя сначала собрать все абзацы, а затем все таблицы. Нумерация OOXML восстанавливается с учётом numId, abstractNumId и restart.

REQ-PARSE-02. block_id стабилен внутри parsing_revision. paragraph_id используется для DOCX; table locator содержит table_id, row_index, cell_index. Для PDF pdf_page_index — индекс от 0; displayed_page=pdf_page_index+1; printed_page_number — nullable строка с номером, напечатанным в документе.

REQ-EXT-08-02. DOCX не имеет стабильной пагинации: pdf_page_index=null и printed_page_number=null. Для него обязательна адресация block_id и paragraph_id либо координатами таблицы. Если создан PDF-снимок DOCX, он регистрируется как производный артефакт со своим hash; его страницы не выдаются за страницы оригинального DOCX.

REQ-EXT-08-03. Хранить original_text, search_text и mapping между нормализованным текстом и исходными блоками. Нормализация для retrieval не должна менять оригинал для цитирования. Для OCR цитата маркируется как OCR; пользователь может открыть исходную страницу и проверить распознавание.

REQ-EXT-08-04. Кандидаты parser: PyMuPDF для PDF и python-docx плюс OOXML для DOCX; лицензии и пригодность проверяются до фиксации зависимостей. OCR adapter выбирается после проверки фикстур на иврите. Конкретные версии фиксируются на этапе T01.

## 9 Восстановление структуры документа

REQ-EXT-09-01. StructureExtractor восстанавливает document → section → subsection → clause → subclause → paragraph. Распознавать номера 3, 3.1, 3.1.2, 12.5.1, 30.11 без смешивания с десятичными числами и датами.

REQ-EXT-09-02. Использовать совместно форматирование, heading styles, numbering, regex, переносы, соседние блоки, длину и контекст. Исходное форматирование не считается надёжным. Неуверенные границы сохраняются с confidence, исходный порядок и текст не меняются.

## 10 Ошибки структуры

REQ-EXT-10-01. structure_confidence: high | medium | low. При отсутствии структуры сохранять section=null, clause=null, structure_confidence=low и исходный блок. Не удалять текст только потому, что номер пункта не распознан; фиксировать предупреждение для последующей проверки.

## 11 Структурное разбиение на chunks

REQ-EXT-11-01. Разбивать юридический текст прежде всего по структуре: пункт → подпункт → логический абзац → размерное разбиение. Пункт, который помещается в CHUNK_MAX_TOKENS, сохраняется целиком. Например, положение 12.5.1 версии 08.2025 остаётся одним chunk с section=12 и clause=12.5.1.

REQ-EXT-11-02. Таблица сохраняет контекст заголовков и связанный пункт; если делится по строкам, каждой части передаётся ссылка на исходные ячейки. Текст соседнего раздела нельзя присоединять только ради заполнения token limit.

## 12 Разбиение больших блоков

REQ-EXT-12-01. Большой пункт делится на parts 1..N. Все parts сохраняют document_id, исходные locators, section и clause. Overlap допустим внутри одного разделяемого блока; размеры и overlap задаются токенами конфигурации раздела 13. Номер страницы для DOCX не создаётся.

## 13 Метаданные и идентичность chunk

REQ-CHUNK-01. Chunk содержит chunk_id, document_id, document_family_id, project_id, parsing_revision, index_generation_id, version_label, document_type, document_role, version_status, legal_status, verification_status, category, language, section, clause, part, source_id, source_url, content_sha256, structure_confidence и text.

REQ-EXT-13-01. text — поисковый текст. Исходные цитируемые блоки и точный mapping хранятся в PostgreSQL. Payload дополнительно содержит block_ids и locator: pdf_page_index, printed_page_number, paragraph_id; все неприменимые значения null. Для chunk на нескольких страницах сохраняются locators всех исходных диапазонов.

REQ-EXT-13-02. chunk_id = UUIDv5(document_id, parsing_revision, chunking_fingerprint, ordered_block_ids, part, content_sha256). Qdrant point_id = UUIDv5(chunk_id, index_generation_id). Повтор задания с теми же параметрами делает upsert той же точки и не создаёт дубль.

REQ-EXT-13-03. fingerprint фиксирует parser/chunker версии, tokenizer, размер, overlap и normalization. Overlap разрешён только между частями одного большого блока; overlap не дублируется в цитате и отчёте сравнения.

REQ-EXT-13-04. Настройки chunking измеряются в токенах выбранного tokenizer. Стартовые настройки CHUNK_MAX_TOKENS=800, CHUNK_OVERLAP_TOKENS=100; они проверяются benchmark и лимитом embedding-модели. Заголовки для поискового контекста отделяются от цитируемого исходного текста.

## 14 Выбор embedding модели

REQ-EXT-14-01. Embedding выполняется локальной моделью для документов и поисковых запросов на иврите, без внешнего API-ключа. Обязательны качественный Hebrew retrieval, batch processing, фиксированная revision и известная размерность. Иноязычные вопросы переводятся на иврит до embed_queries; модель ответа не создаёт embeddings.

REQ-EXT-14-02. Модель выбирается по dataset T05 до полной векторизации корпуса. Заполнить EMBEDDING_PROVIDER, MODEL, REVISION и DIMENSION; смена модели требует нового fingerprint и процедуры миграции раздела 15, а не простой замены строки конфигурации.

## 15 Коллекции и индексы Qdrant

REQ-INDEX-01. Использовать Qdrant с named dense vector и named sparse vector lexical. Dense: размерность выбранной embedding-модели, distance=Cosine. Sparse: lexical encoder раздела 21; произвольные dense vectors разных моделей не смешивать.

REQ-EXT-15-01. Логическое имя pinui_documents — alias активной физической коллекции pinui_documents_<fingerprint>. Коллекция создаётся идемпотентной командой; несовместимая схема вызывает ошибку, а не незаметное пересоздание.

REQ-EXT-15-02. Payload indexes: document_id, document_family_id, project_id, index_generation_id, document_type, document_role, version_status, legal_status, verification_status, category, language. UUID и enum индексируются как keyword.

REQ-EXT-15-03. Для нового embedding fingerprint создаётся другая физическая коллекция, выполняется индексация и benchmark, затем переключается alias. Предыдущая коллекция сохраняется до проверки и может быть использована для отката. Смена размерности через одну env-переменную без миграции запрещена.

REQ-EXT-15-04. Обновление одного документа создаёт новую index_generation в активной коллекции и переключает указатель реестра после проверки полноты. Запрос всегда фильтрует по разрешённым document_id и активным index_generation_id.

## 16 Первичное создание векторной базы

REQ-EXT-16-01. Создать registry и collection schema; выполнить parsing → structure → chunking → metadata → batch dense embeddings и lexical vectors → Qdrant staging → integrity verification → activation.

REQ-EXT-16-02. Проверять количество документов, исходных блоков, chunks и точек; оба типа vectors, размерность, metadata, locators, hashes, дубли и документы без индекса. Отчёт первичной индексации сохраняется как manifest с fingerprints. Документ без готового проверенного индекса не участвует в поиске.

## 17 Индексация обновления и восстановление

REQ-ING-02. Содержимое редакции неизменяемо. Изменение исходного файла → новая редакция с новым document_id; изменение технических метаданных → обновление записи и audit event. Исправление parser или chunker → новая parsing_revision и index_generation для того же document_id.

REQ-EXT-17-01. ingestion_status: registered | parsing | parsed | indexing | ready | failed. Подробный текущий шаг и ошибка принадлежат job. parsing_failed — error_code, а не юридический статус.

REQ-ING-03. Новая generation сначала записывает блоки, chunks и vectors в неактивную область. После проверки количества, hashes, locators и наличия обоих vectors PostgreSQL транзакционно переключает active_index_generation_id и помечает ingestion_status=ready. При смене редакции в той же транзакции переключается current_document_id.

REQ-EXT-17-02. PostgreSQL и Qdrant не имеют общей транзакции. Использовать job checkpoints и reconciliation: незавершённая generation не участвует в retrieval, повторный worker возобновляет upsert, периодическая проверка удаляет только подтверждённые orphan generations после срока хранения. Старые chunks не удалять до успешной активации замены.

REQ-ING-04. Query фиксирует snapshot разрешённых document_id и generations на начало запроса, применяет его ко всем dense/sparse поискам и повторно проверяет доступ и готовность результатов в реестре. Если источник изменился во время запроса и уже не допустим для current_norms, один раз повторить retrieval; иначе вернуть SOURCE_CHANGED. Смешивание поколений запрещено.

REQ-EXT-17-03. Повтор одинаковой загрузки в том же семействе по hash возвращает существующий document_id; дубль в другом проекте не должен раскрывать наличие чужого документа. Старые редакции сохраняются для сравнения.

## 18 Обработка пользовательского запроса

REQ-EXT-18-01. Question → language detection → intent → document/entity resolution → authorization Scope → translation to Hebrew when needed → bounded Hebrew query rewrite → retrieval → reranking → evidence context → LLM → evidence validation → response. Разрешение IDs и проверка области предшествуют поиску.

REQ-EXT-18-02. Пример вопроса: «Каковы права пожилого собственника при пинуй-бинуй?». Если вопрос требует действующих норм, использовать current_norms; если он относится к конкретному договору, явно выбрать документ или проект. При неоднозначности не угадывать редакцию.

## 19 Языки обращения и язык корпуса

REQ-LANG-01. Корпус, индексируемый текст и запрос retrieval имеют язык he. Язык обращения не ограничен русским: приложение принимает языки из SUPPORTED_QUERY_LANGUAGES, проверенные для выбранной LLM. Русский и иврит — обязательные контрольные языки, остальные добавляются после проверки качества; не обещать поддержку любого языка без проверки.

REQ-EXT-19-01. При language=auto определять язык оригинального вопроса и использовать его для ответа. Явный language задаёт предпочтительный язык ответа и не подменяет язык исходного вопроса. Для неоднозначного короткого или смешанного вопроса учитывать выбранный язык UI либо возвращать уточнение. Неподдерживаемый язык → 422 UNSUPPORTED_LANGUAGE.

REQ-LANG-02. TranslationAdapter переводит исходный вопрос на иврит перед retrieval; вопрос на иврите перевод не требует. Сохранять original_question, detected_language, answer_language и search_question_he. Перевод не изменяет даты, числа, имена, номера пунктов, выбранные IDs и Scope. При ошибке перевода вернуть TRANSLATION_UNAVAILABLE, не искать исходный иноязычный текст как будто он на иврите. Все query variants и вход reranker — на иврите.

REQ-LANG-03. LLM получает evidence на иврите и формирует ответ на answer_language. Оригинальные citations.quote всегда на иврите; quote_translation допустим отдельно с пометкой и кодом языка. Перевод не заменяет источник, locator или оригинальные spans. Проверять соответствие смысла ответа и перевода оригинальному evidence.

REQ-LANG-04. OPENAI_API_KEY необязателен при запуске. Без него доступны UI, загрузка, локальная индексация и поиск на иврите с исходными фрагментами и источниками. Генерация ответа и перевод недоступны: не подменять их mock или общими знаниями. Неивритский запрос и явно запрошенная генерация без ключа → 409 LLM_NOT_CONFIGURED; UI объясняет необходимость настройки ключа. При наличии ключа перевод и генерация доступны после проверки конфигурации и бюджета. Ошибка настроенного провайдера возвращается явно, а не скрыто превращается в режим без ключа.

## 20 Переформулирование и расширение запроса

REQ-EXT-20-01. Исходный вопрос всегда сохраняется. Перевод на иврит обязателен для неивритского вопроса и не зависит от USE_QUERY_EXPANSION. Допустимо ограниченное добавление юридических терминов на иврите; новые варианты не должны менять document filters, числа, даты или смысл вопроса.

REQ-EXT-20-02. Пример «Можно ли уменьшить обещанную площадь новой квартиры?» может сопоставляться с תוספת שטח, דירת הבעלים החדשה, רווחיות מינימלית, שמאי, תמורה. Это поисковые подсказки, не заранее установленные основания ответа. Эффект expansion проверяется ablation benchmark.

## 21 Hybrid retrieval и lexical encoder

REQ-RET-01. Hybrid search реализуется в Qdrant через dense и sparse prefetch и rank fusion RRF. PostgreSQL FTS и отдельный Elasticsearch в базовую архитектуру не входят. Одинаковые ограничения доступа, документа, поколения и актуальности применяются к каждой ветке до поиска.

REQ-EXT-21-01. Для воспроизводимого Hebrew lexical retrieval использовать локальный BM25-compatible sparse encoder. Unicode NFC, casefold для латиницы/кириллицы; выделять слова, числа, проценты и номера пунктов вроде 12.5.1. Для иврита сохранять полный токен без обязательного stemming; снимать niqqud только в search_text. Stopwords по умолчанию выключены.

REQ-EXT-21-02. Индекс vocabulary хранится в PostgreSQL: token → integer dimension; IDs не перенумеровывать. Нужные новые токены добавлять атомарно с unique(token). Версия vocabulary/normalization фиксируется в fingerprint. Query неизвестные токены пропускает, не создавая новые dimensions.

REQ-EXT-21-03. Документный sparse вес: tf*(k1+1)/(tf+k1*(1-b+b*length/avg_length)); k1=1.2, b=0.75. Query sparse weights=1 для уникальных токенов. IDF рассчитывает Qdrant через modifier=IDF; двойное применение IDF запрещено. avg_length фиксируется для generation корпуса; изменение этой статистики требует новой lexical generation и benchmark. Такой encoder — проверяемое начальное решение, а не обещание оптимального поиска на иврите.

REQ-EXT-21-04. Поиск использует search_question_he и не более двух rewritten queries на иврите. Для исходного вопроса на иврите search_question_he совпадает с ним. Дедуплицировать варианты. Для каждого варианта выполнить dense/sparse RRF в Qdrant; затем объединить списки вариантов по rank-based RRF в приложении с явно заданным k=60 и одинаковыми весами. Числовые scores различных моделей не складывать.

REQ-EXT-21-05. DENSE_TOP_K=30, SPARSE_TOP_K=30, RETRIEVAL_TOP_K=30 — стартовые настройки. Дедупликация по chunk_id и generation; exact clause lookup выполняется отдельно по структурным полям, но с теми же фильтрами. RRF score не является вероятностью релевантности и не используется как единый MIN_RELEVANCE_SCORE.

## 22 Reranker и пороги релевантности

REQ-RET-02. Локальный Reranker adapter принимает search_question_he и до RETRIEVAL_TOP_K candidates с IDs, возвращает упорядоченные candidates и raw_score. Для обеих поисковых веток и reranking используется один подтверждённый перевод на иврит; оригинальный вопрос сохраняется для ответа и диагностики.

REQ-EXT-22-01. RERANKER_PROVIDER и RERANKER_MODEL выбираются на T05 по benchmark поиска на иврите и переведённых вопросов. Обязательно сравнить исходный dense+lexical baseline и reranked результат; название выбранной модели, revision, лицензию, порог и ресурсные требования записать в docs/model-decisions.md.

REQ-EXT-22-02. В контекст идут до RERANK_TOP_K=7 chunks с учётом token budget. RERANK_MIN_SCORE калибруется на отрицательных и положительных примерах конкретной модели; универсального порога для всех providers нет. Пустой отбор → insufficient_evidence.

REQ-EXT-22-03. Отключение reranker допустимо для ablation и диагностики. В принятой финальной конфигурации reranker обязателен. Его недоступность вызывает RERANKER_UNAVAILABLE; скрытое обходное поведение запрещено.

## 23 Основная LLM и fallback

REQ-EXT-23-01. LLM используется для перевода вопросов на иврит и генерации ответов на языке обращения по найденному evidence. Отсутствие ключа не препятствует локальной индексации и поиску на иврите. Основная LLM: gpt-5.4-mini; fallback: gpt-4.1-mini. Выбор задан исходной спецификацией и сохранён. Модели задаются настройками, их доступность проверяется в выбранном аккаунте на T09.

REQ-EXT-23-02. LLM не выполняет первичный поиск документов и не получает весь corpus. Fallback вызывается по правилам раздела 45 и должен соблюдать тот же evidence contract. Стоимость и tokens учитываются для фактически использованной модели.

## 24 Правила генерации

REQ-EXT-24-01. System prompt требует использовать только переданный evidence context, не добавлять факты из общей памяти, не смешивать документы и редакции, не придумывать IDs/locators и сообщать о недостаточности данных. Ответ формируется на языке пользователя.

REQ-EXT-24-02. Инструкции внутри документов трактуются как цитируемые данные. Модель возвращает ProposedClaims по schema; источник и quote формирует backend. Prompt version и model fingerprint фиксируются для regression.

## 25 Формирование ответа

REQ-EXT-25-01. Пользователь видит ответ и объяснение из проверенных claims, привязанные цитаты и сведения об источниках. Каждое существенное фактическое утверждение имеет citation_ids.

Источник указывать всегда: название документа, орган/автор, редакция или дата, страница/пункт и ссылка на оригинал либо доступный локальный документ. Явно обозначать тип источника: закон/нормативный акт, стандарт, официальная рекомендация, решение по профессиональной этике, образец договора или договор проекта. Рекомендации и образцы не представлять как обязательную норму или подписанные условия проекта. Для тематического сравнения источник нужен для каждой стороны и вывода о различии; неподтверждённое утверждение исключать из ответа.

REQ-EXT-25-02. Иллюстративный ответ о парковке может содержать «В договоре 08.2025 предусмотрена одна парковка» только если реальный найденный текст это подтверждает. Текст примера спецификации не является источником и не должен попадать в corpus как условие договора.

## 26 Цитирование и проверка доказательств

REQ-CITE-01. LLM возвращает структурированные claims: claim_id, text, evidence_ids. Каждый evidence_id выбирается из ограниченного enum готовых выдержек конкретного запроса. Backend сам восстанавливает разрешённые chunk_id/block_id и точные span_start/span_end из immutable evidence context; модель не рассчитывает Unicode offsets. Метаданные источника, страницы и quote backend достраивает из сохранённого original_text, проверяя scope и точное совпадение. Неизвестные evidence IDs не принимаются; claims с недействительными ссылками целиком исключаются.

REQ-EXT-26-01. Offsets задаются как [start,end) по Unicode code points внутри конкретного block.original_text. Span должен быть в границах блока и предоставленного модели контекста. Проверка диапазона и точного совпадения обязательна до ответа. HTML и bidi rendering не меняют сохранённый оригинал.

REQ-EXT-26-02. Источник содержит citation_id, document_id, version_label, title, chunk_id, block_id, quote, locator и source_url. Locator: pdf_page_index, displayed_page, printed_page_number, section, clause, paragraph_id, table_id, row_index, cell_index; неприменимые поля null. PDF page обязателен; DOCX адресуется абзацем или таблицей.

REQ-CITE-02. Проверка существования цитаты не доказывает, что она подтверждает claim. Проверять evidence coverage и соответствие смысла в benchmark с ручной оценкой; при сомнении не выдавать категорический вывод. После одной ограниченной попытки исправления невалидный claim исключается; если доказательств не осталось — insufficient_evidence. Пользователю сообщать о неполном подтверждении.

REQ-EXT-26-03. Ответ на любом поддерживаемом языке сохраняет цитаты в оригинале на иврите. Перевод цитаты разрешён только в отдельном поле quote_translation с явной пометкой. Цитата OCR маркируется extraction_method=ocr и имеет ссылку на страницу оригинала. Цитаты и результаты проверки сохраняются с request_id.

## 27 Поиск внутри документа

REQ-EXT-27-01. Вопрос «Что говорится о парковке в 08.2025?» разрешается в UUID выбранного августовского документа через aliases. Этот document_id фиксируется в Scope обеих поисковых веток и reranker. Поиск в других редакциях при таком выборе запрещён.

## 28 Сравнение двух версий

REQ-CMP-01. Для тематического сравнения двух редакций retrieval и reranking выполняются отдельно в Scope A и Scope B. В LLM поступают отдельно маркированные evidence contexts; нельзя сначала смешивать chunks и затем угадывать принадлежность.

REQ-EXT-28-01. Ответ содержит положение A с citations_a, положение B с citations_b и описание отличия. Если top-K не нашёл положение, сообщить только о недостатке найденных данных; отсутствие в документе требует отдельной проверки полного текста.

## 29 Выдача тематического сравнения

REQ-EXT-29-01. Для каждой темы показать условие A и citation_a, условие B и citation_b, затем описание подтверждённого смыслового отличия. Если положение не найдено в одной retrieval ветке, использовать формулировку «В найденных фрагментах версии A положение не обнаружено»; не объявлять его отсутствующим во всём договоре.

## 30 Границы тематического сравнения

REQ-CMP-02. Сервис сравнивает выбранную тему или конкретный вопрос в двух документах. Полное сравнение договоров, исчерпывающий список всех изменений, выравнивание всех пунктов и доказательство отсутствия условия во всём документе не входят в объём проекта.

REQ-EXT-30-01. Запрос без темы, например «Чем отличаются договоры 04.2025 и 08.2025?», возвращает clarification_required с предложением указать тему: площадь, парковка, сроки, гарантии либо иной вопрос. Retrieval и генерация сравнения запускаются после уточнения; модель не выбирает тему молча.

REQ-EXT-30-02. Для каждого finding сохранять раздельные statements и citations A/B. Если в одной ветке нет подтверждающих фрагментов, statement соответствующей стороны=null, citations пусты, evidence_status_a/b=found|not_found_in_retrieval. Difference допускается только при подтверждении обеих сторон; иначе difference=null и явно сообщается о недостатке найденных данных. При отсутствии evidence с обеих сторон — insufficient_evidence. Не использовать added/removed как вывод из retrieval miss.

REQ-EXT-30-03. Изменение нумерации, таблицы и приложения обрабатываются поиском по теме с исходными locators; отдельный StructureAligner не требуется. Не заявлять 100% покрытия договора или обнаружения всех изменений.

REQ-EXT-31-01. Представление результата REQ-EXT-31-01–02: выводы группировать по документам и редакциям, привязывать пронумерованные ссылки к каждому выводу. Договоры, рекомендации и образцы явно различать. Полный исходный текст цитаты на иврите и реквизиты доступны в раскрывающемся блоке. Для языка обращения, отличного от иврита, можно добавить отдельные quote_excerpt (точная подстрока quote до 240 символов), quote_translation и title_translation после проверки языка, чисел и смысловой верности. Они не заменяют quote и не меняют координаты Citation. Если проверка/бюджет не позволяет подготовить перевод, сохранить проверенный ответ и оригинал; при исчерпании бюджета пояснить причину человеку.

REQ-API-01. FastAPI /api/v1; Pydantic v2 модели являются источником OpenAPI. UI работает только через HTTP API. Все ошибки имеют единую структуру: error.code, error.message, error.details и request_id.

GET /health — liveness без секретов; GET /status — readiness PostgreSQL/Qdrant/worker/local_models/config, 200 либо 503; capabilities отдельно показывает search_he, translation и answer_generation. REQ-EXT-33-07. POST для тяжёлых операций принимает Idempotency-Key. unique(actor_id,route,key), request_hash и сохранённый ответ находятся в PostgreSQL: повтор одинакового запроса возвращает тот же job; другое тело с тем же ключом → 409 IDEMPOTENCY_CONFLICT. REQ-EXT-33-08. 401 — нет аутентификации; 403 — нет роли; 404 — объект отсутствует либо недоступен; 409 — конфликт/документ не ready; 413 — превышение upload size; 415 — формат; 422 — невалидные фильтры; 429 — лимит; 502/503/504 — provider/infra/timeout. clarification_required и insufficient_evidence являются нормальными ответами 200.

## 34 Контракт запроса и ответа

REQ-API-02. QueryRequest содержит response_mode: auto|answer|search (default=auto), question: string длиной 1..4000, project_id: UUID|null, document_ids: list[UUID] не более 20, document_family_id: UUID|null, category: string|null, mode: all_documents|current_norms|project_documents|historical, as_of: date|null, language: auto либо поддерживаемый код BCP 47, debug: bool=false.

REQ-EXT-34-01. Решение пользователя 10.10.2026: если mode не передан, явный project_id/document_ids выбирает project_documents, иначе all_documents. В UI по умолчанию all_documents: все доступные документы, включая договоры, рекомендации и подтверждённые нормы. Непроверенные исходные законы, требующие legal engine, исключены; corpus incomplete явно обозначен. Тип и актуальность каждого источника сохраняются; рекомендации и условия договора не выдаются за закон. current_norms остаётся отдельным строгим режимом. Для project_documents нужны явный проект либо document_ids.

REQ-EXT-34-02. Все фильтры объединяются AND; OR внутри document_ids. Пустой доступный набор не расширяется на весь корпус. project_id включает документы этого проекта и общие нормативы только при явно указанном include_shared_norms=true; это дополнительное boolean поле с default=false.

REQ-EXT-34-03. response_mode=auto выбирает answer при настроенной LLM, иначе search. Режим search принимает только исходный вопрос на иврите, обходится без внешних вызовов и возвращает status=search_results, language=he, answer=null, claims=[], sources с найденными выдержками. При отсутствии результатов — insufficient_evidence. answer без ключа → 409 LLM_NOT_CONFIGURED.

REQ-EXT-34-04. QueryResponse: request_id, status=answered|search_results|insufficient_evidence|clarification_required, language — поддерживаемый код BCP 47, answer, claims, sources, warnings, clarification_candidates, debug_trace|null, usage. claims содержит claim_id, text и citation_ids. Для search claims пуст; sources представляют результаты поиска, а не доказательства сгенерированных claims. answer строится из проверенных claims, а не из отдельного непроверенного free-text поля LLM.

REQ-EXT-34-05. sources — список Citation из раздела 26. clarification_candidates содержит только доступные пользователю документы. usage: provider, model, input_tokens, output_tokens, cached_input_tokens если доступны, estimated_cost и currency; неизвестная стоимость null, не 0.

REQ-EXT-34-06. Пример входа: {"question":"Что сказано о парковке?","document_ids":["11111111-1111-4111-8111-111111111111"],"mode":"project_documents","language":"ru","debug":false}. UUID иллюстративный, не ID реального файла.

REQ-EXT-34-07. Пример источника DOCX: {"citation_id":"c1","document_id":"11111111-1111-4111-8111-111111111111","version_label":"08.2025","block_id":"b42","quote":"исходный текст","locator":{"pdf_page_index":null,"section":"12","clause":"12.5.1","paragraph_id":"p42"}}. Пример сокращён; полную схему генерирует OpenAPI.

## 35 Контракты сравнения

REQ-EXT-35-01. Тематическое сравнение требует настроенной LLM; без ключа → 409 LLM_NOT_CONFIGURED. Вопрос переводится на иврит один раз до двух независимых поисковых веток; язык ответа определяется исходным вопросом либо явным language.

REQ-API-03. CompareRequest: question, document_a: UUID, document_b: UUID, language: auto либо поддерживаемый код BCP 47, debug: bool. Оба документа должны быть ready и доступны actor. Если IDs совпадают → 422 SAME_DOCUMENT.

REQ-EXT-35-02. CompareResponse: request_id, status, language, findings[], warnings, usage. Finding содержит topic, statement_a, statement_b, difference, citations_a, citations_b, evidence_status_a, evidence_status_b по разделу 30. status=compared|insufficient_evidence|clarification_required; clarification_topics содержит предлагаемые темы, а findings=[] до уточнения. Для тематического поиска отсутствие найденного положения означает not_found_in_retrieval, а не доказательство отсутствия в документе.

REQ-EXT-40-02. Integration: PostgreSQL migrations/constraints, document→Qdrant, dense/sparse filters, jobs recovery/activation, reranker adapter, retrieval→LLM contract и compare pipeline.

REQ-EXT-40-03. E2E: upload→job→ready→question→validated claims/citations; выбор версии, access denial, source freshness и тематическое сравнение. Использовать реальные PostgreSQL/Qdrant в integration и безопасные fixtures. Качество моделей проверяется отдельным benchmark раздела 41.

## 41 Версионируемый benchmark

REQ-QA-01. Создать dataset до выбора embeddings и до настройки retrieval. Не менее 60 размеченных запросов для разработки и 30 отдельных holdout запросов; языковые направления HE→HE и каждый поддерживаемый язык→HE; ответ на языке обращения, разговорные вопросы, точные пункты/числа, версии, отрицательные вопросы и сравнение. Это минимальный размер проекта, а не гарантия статистической точности.

REQ-EXT-41-01. JSONL record: case_id, question, language, expected_search_question_he, intent, scope, expected_document_ids, expected_block_ids, answerability, expected_claims, expected_citations, tags. Block IDs привязаны к dataset parsing_revision; оценка по blocks не ломается при изменении chunking. Chunk relevance вычисляется через block overlap.

REQ-EXT-41-02. Train/dev и holdout делятся до настройки и не содержат почти одинаковые вопросы. Разметка и исходные фикстуры версионируются; спорные примеры помечаются, не используются для автоматического pass/fail до проверки.

REQ-EXT-41-03. Сравнивать dense-only, lexical-only, hybrid, hybrid+reranker и Hebrew query expansion; отдельно оценивать влияние перевода на retrieval; фиксировать hardware, fingerprints, модели и настройки. Report содержит per-case results и агрегаты по языкам и типам запроса.

REQ-QA-02. Изменение parser, chunking, embedding, lexical normalization, query rewrite, filters, reranker либо prompts требует regression benchmark и сравнения с approved baseline. Unit/integration CI использует детерминированные fakes без внешних платных запросов; real-provider evaluation запускается отдельной командой с бюджетом.

REQ-EXT-41-04. Тематическое сравнение имеет golden cases: разные условия по одной теме, одинаковые условия, изменённые числа, отсутствие найденных фрагментов в одной или обеих версиях, неоднозначный вопрос без темы, таблицы и OCR. Ручная проверка раздельных цитат A/B и смыслового отличия обязательна; LLM judge не является единственным критерием приёмки.

## 42 Метрики поиска

REQ-EXT-42-01. Основные метрики: Recall@5, Recall@10, MRR. Дополнительно: правильный документ, редакция и пункт, cross-language accuracy. Для min_topic_compare_correctness считать долю размеченных тематических cases с корректными statements A/B, подтверждённым difference либо корректным сообщением о недостатке evidence; оценивать вручную по эталону и отдельно проверять уточнение вопроса без темы. Отчёты приводят значения по всем cases и отдельно по языкам/типам, чтобы общая средняя не скрывала ухудшение HE.

## 43 Метрики ответа

REQ-EXT-43-01. Проверять groundedness, factual correctness, citation correctness/completeness, язык ответа, неподтверждённые claims и смешивание редакций. Точное совпадение quote с оригиналом проверяется автоматически; смысловое соответствие claim и источника — размеченными cases и ручной проверкой.

## 44 Производительность и профиль приёмки

REQ-PERF-01. Логировать latency каждого шага, total p50/p95, очередь и длительность jobs, tokens/cost. Для benchmarks фиксировать CPU/RAM, corpus pages/chunks, concurrent users (1–2), provider/model и дату измерения.

REQ-EXT-44-01. benchmarks/acceptance-profile.yaml содержит обязательные значения: corpus_size, concurrent_queries, query_p95_seconds, indexing_pages_per_minute, topic_compare_p95_seconds, daily_cost_limit, request_cost_limit и качество по разделу 53. Если профиль не заполнен, функциональная разработка продолжается, но финальная performance/cost приёмка не проходит.

REQ-EXT-44-02. T05 измеряет baseline, T14 фиксирует итоговый профиль и обоснование выбранных значений. Не объявлять «быстро» без числа и среды измерения; QUERY_TIMEOUT_SECONDS является timeout, а не целевым p95.

REQ-EXT-44-03. Размер контекста ограничен независимо от объёма корпуса. Сначала резервировать системный prompt и output budget, затем добавлять chunks целиком либо по проверяемым исходным диапазонам; обрезание цитаты без изменения span запрещено.

REQ-EXT-44-04. При перегрузке запросы получают 429 либо задания остаются pending. Worker concurrency и provider rate limit регулируются конфигурацией; очередь не должна терять jobs после перезапуска.

## 45 Ошибки и ограниченные повторы

REQ-EXT-45-01. Ошибки parsing/structure/OCR фиксируются с document_id, page/block и job_id. Частично извлечённый документ не активируется как полный без явного разрешения и маркировки. В тематическом сравнении предупреждать о неполном извлечении каждой редакции; retrieval miss не доказывает отсутствие условия.

REQ-EXT-45-02. Qdrant или PostgreSQL недоступен → 503, без LLM ответа из общей памяти. Нет подтверждающих chunks → status=insufficient_evidence на языке вопроса. Неоднозначное название → clarification_required. Документ не ready → 409 DOCUMENT_NOT_READY.

REQ-EXT-45-03. Provider transient ошибки повторять не более PROVIDER_MAX_ATTEMPTS с backoff+jitter и учётом Retry-After. 401/403, некорректный model ID и ошибки контракта не повторять как временные. Fallback фиксируется в warnings и usage; он не расширяет доказательства.

REQ-EXT-45-04. Задание после исчерпания retries становится failed с retryable, error_code и checkpoint. Истёкший lease возвращает работу в очередь; запретить одновременную активацию двух generations для одной редакции через транзакционную блокировку.

REQ-EXT-45-05. Детальный текст источников для диагностики хранить только в защищённой области с retention; production logs содержат IDs, timings и error codes. Пользовательская ошибка не раскрывает секреты, local paths и чужие документы.

## 46 Безопасность

REQ-EXT-46-01. Секреты хранятся в environment/secret storage и не попадают в Git. Административные endpoints, debug, документы проектов и оригиналы защищены auth/grants. Upload и acquisition ограничивают форматы, размеры, распаковку и внешние адреса.

REQ-EXT-46-02. Содержимое документов не выполняется. Персональные данные не передаются в model context и не выводятся пользователю без необходимости для запрошенной функции; маскирование для внешних вызовов оформляется отдельным preprocessing policy с mapping для локальных citations. Дополнительные конкретные меры заданы в разделе 57.

## 47 Персональные данные договоров

REQ-EXT-47-01. Реальные договоры могут содержать ФИО, номера удостоверений, адреса и сведения о собственности. Публичная демонстрация использует обезличенные документы. Оригинал с персональными данными не публикуется через viewer публичного Demo.

## 49 Критерии приёмки законченного сервиса

REQ-ACC-01. Вопросы на поддерживаемых языках, перевод на иврит, ответы на языке обращения, поиск на иврите без API-ключа, поиск по документу/редакции/проекту, актуальные нормы, тематическое сравнение работают через один backend. UI и API проверены на реальном обезличенном корпусе פינוי־בינוי.

REQ-ACC-02. Все существенные claims имеют проверенные citations; несуществующие spans, номера страниц и пункты отклоняются. PDF указывает страницу и пункт при наличии; DOCX указывает абзац/таблицу и пункт, без выдуманной страницы. Недостаток данных не заменяется общими знаниями LLM.

REQ-ACC-03. Версии 04.2025 и 08.2025 выбираются отдельно; aliases разрешаются в области проекта; результаты не смешиваются. Нормы unknown/stale/repealed исключаются из current_norms. Новая редакция заменяет старую только после готовности и подтверждения.

REQ-ACC-04. Повтор загрузки/job не создаёт дубль. Reindex одного документа не требует перестройки корпуса. Перезапуск worker, ошибки provider и частичная запись Qdrant не активируют неполные generations. Миграция embedding модели имеет проверенный rollback.

REQ-ACC-05. Hybrid retrieval и reranker приняты на benchmark поиска на иврите и переведённых вопросов; gpt-5.4-mini и fallback проходят контрактный smoke test в выбранном аккаунте. Разработчик фиксирует модели и точные версии зависимостей, результаты holdout и согласованный acceptance-profile.

REQ-ACC-06. Тематическое сравнение показывает подтверждённые условия и цитаты из каждой редакции, явно сообщает о недостатке найденных данных и требует уточнения для вопроса без темы. Auth, project grants и debug ограничения действуют до retrieval. Backup и restore проверены, секретов/персональных данных в Git нет.

REQ-ACC-07. T01–T14 завершены с проверками, requirements-traceability заполнена, обязательные TODO/TBD отсутствуют. Непроверенные модели, незаполненный allowlist или неутверждённые performance limits исключают объявление проекта завершённым.

## 51 Контракты модулей и инварианты

REQ-CONTRACT-01. DTO определяются в app/models; модули зависят от Protocol, а не от конкретного SDK. Исключения на границе adapter переводятся в единые domain errors. Все IO асинхронны либо вынесены в worker; CPU-heavy parsing не блокирует event loop API.

REQ-EXT-51-01. DocumentParser.parse(raw_ref, parser_config) → ParsedDocument(document_id, parsing_revision, ordered_blocks, extraction_warnings). Block: block_id, original_text, search_text, normalization_map, locator, extraction_method, structure_confidence.

REQ-EXT-51-02. StructureExtractor.extract(ParsedDocument) → StructuredDocument(nodes, ordered_block_ids, warnings). Chunker.split(StructuredDocument, ChunkConfig) → ChunkDraft[] с ordered spans и fingerprint.

REQ-EXT-51-03. EmbeddingProvider.embed_documents(texts) / embed_queries(texts) → vectors; контракт фиксирует model revision, dimension, normalization и provider limits. LexicalEncoder.encode_documents/encode_query использует одну tokenizer/vocabulary policy.

REQ-EXT-51-04. IndexRepository.stage(generation,chunks,vectors) / verify(generation) / search(scope,query) → candidates. Registry.activate(generation) выполняется только после verify. Scope содержит разрешённые document_id и generation snapshots.

REQ-EXT-51-05. TranslationAdapter.translate(question,target_language=he) → SearchQuestion с original_question, detected_language и search_question_he; перевод получает только вопрос, не весь корпус. Reranker.rank(search_question_he,candidates) → ScoredCandidate[]. ContextBuilder.build(candidates,budget) → EvidenceContext с allowlist доступных spans. AnswerGenerator.generate(context,language) → ProposedClaims. EvidenceValidator.validate → VerifiedClaims. CitationBuilder.build → Citation[].

REQ-EXT-51-06. ComparisonService.compare_topic(scope_a,scope_b,search_question_he,answer_language) → CompareResponse; две независимые поисковые ветки, подтверждённые statements A/B и difference. Полный alignment не реализуется.

REQ-EXT-51-07. Инварианты: нельзя цитировать отсутствующий block; нельзя искать вне Scope; нельзя активировать неготовую generation; нельзя изменять raw bytes редакции; нельзя трактовать retrieval miss как доказательство отсутствия положения; нельзя считать current синонимом signed_contract.

## 52 Схема PostgreSQL и ограничения

REQ-EXT-52-01. projects: project_id UUID PK, slug UNIQUE, title, created_at. actors: actor_id, role=admin|reader, token_hash, enabled; project_grants: actor_id+project_id UNIQUE. Общий нормативный корпус доступен reader; договоры — только по grants.

REQ-EXT-52-02. document_families: family_id UUID PK, project_id nullable FK, slug, title, current_document_id nullable FK. Обеспечить scoped uniqueness slug для общего корпуса и проектов через отдельные partial unique indexes; NULL в обычном UNIQUE недостаточен.

REQ-EXT-52-03. document_versions: document_id UUID PK, family_id FK, поля раздела 5, active_parsing_revision, active_index_generation_id. UNIQUE(family_id,file_sha256). FK или constraint trigger гарантирует принадлежность current_document_id тому же family; роли и статусы ограничены CHECK.

REQ-EXT-52-04. document_aliases: alias_id, family_id FK, normalized_alias, document_id FK; UNIQUE(family_id,normalized_alias,document_id). Один alias может давать несколько кандидатов — resolver обязан вернуть уточнение.

REQ-EXT-52-05. parsing_revisions: parsing_revision UUID PK, document_id FK, parser_fingerprint, quality, manifest_key. blocks: parsing_revision+block_id PK, ordinal, parent_node_id, original_text, search_text, normalization_map JSONB, locator JSONB. Индекс ordinal задаёт исходный порядок.

REQ-EXT-52-06. index_generations: generation_id UUID PK, document_id FK, parsing_revision FK, fingerprint, collection_name, status=staging|ready|active|retired|failed, expected_count, verified_count. Частичный UNIQUE(document_id) WHERE status='active'; реестр проверяет совпадение ссылок.

REQ-EXT-52-07. chunks: chunk_id UUID PK, parsing_revision FK, chunking_fingerprint, text, content_sha256, spans JSONB; generation_chunks: generation_id+chunk_id PK, point_id UUID UNIQUE. Нельзя overwrite исходные spans старого chunk при reindex.

REQ-EXT-52-08. source_registry, source_checks, jobs, job_checkpoints, idempotency_records, comparison_reports (тематические результаты с request_id, snapshots A/B и вопросом), comparison_items (findings с раздельными citations), audit_events, lexical_vocabulary, lexical_generations — отдельные таблицы с FK и created_at. Job хранит attempt, lease_until, heartbeat_at, request_hash и safe error details.

REQ-EXT-52-09. Все изменения current, generation и статусов пишут audit event в той же PostgreSQL транзакции. Проверки доступа выполняются repository/service до выдачи ID. Деструктивное удаление исходников не входит в автоматический reindex.

REQ-EXT-52-10. Миграции проверять на пустой базе и на предыдущей schema revision. Не использовать create_all как production миграцию; downgrade, если невозможен без потери данных, документировать и использовать восстановление backup.

## 53 Измеримые проверки и baseline

REQ-QA-03. Автоматические строгие gates: 100% корректных citation offsets/metadata на golden fixtures; 0 нарушений Scope/версий/доступа; 0 дублей после повторов jobs; 0 смешений цитат A/B и 0 утверждений об отсутствии условия на основании retrieval miss в тематических comparison fixtures. Эти gates не заменяют оценку смысла ответа.

REQ-EXT-53-01. Качество retrieval измерять Recall@5, Recall@10, MRR по ожидаемым blocks и отдельно по языковым направлениям. Groundedness, citation completeness и корректность смысловых изменений оценивать размеченными cases с ручной проверкой. Negative cases должны давать insufficient_evidence без неподтверждённых claims.

REQ-EXT-53-02. После T05 фиксировать immutable baseline manifest: dataset commit/hash, corpus hashes, model fingerprints, settings, hardware и результаты. baseline нельзя автоматически перезаписывать в тесте ради зелёного результата.

REQ-EXT-53-03. Кандидат не принимается при новых Scope/citation/version нарушениях. Для перевода отдельно проверять сохранение смысла, имён, дат, чисел и пунктов; для каждого дополнительного языка проверять перевод вопроса, retrieval и groundedness ответа до добавления в SUPPORTED_QUERY_LANGUAGES. Приёмка включает запуск без ключа, Hebrew search без внешних вызовов, отказ иноязычного запроса без ключа и ответы на исходном языке с ключом. Для quality регрессии стартовый допуск равен 0 абсолютных процентных пунктов на совокупности и каждом языковом сегменте; изменение допуска требует ADR и явного значения в acceptance-profile. Сравнение проводится на одинаковом dataset и корпусе.

REQ-EXT-53-04. Baseline является условием отсутствия регрессии, но не доказывает достаточность качества. До финальной приёмки отдельно заполнить numeric targets: min_recall_at_10, min_mrr, min_groundedness, min_citation_completeness, min_negative_case_accuracy и min_topic_compare_correctness. Значения обосновываются измерениями и фиксируются в acceptance-profile; пока они отсутствуют, quality gate помечается blocked.

REQ-EXT-53-05. В CI: ruff check, ruff format --check, unit tests; при доступной инфраструктуре integration/E2E. Отдельно: benchmark regression, real-provider smoke, manual semantic review, load tests и restore drill. Моки проверяют протоколы, но не подтверждают качество поиска на иврите, перевода и ответов на поддерживаемых языках.

## 57 Доступ данные и стоимость

REQ-SEC-01. Для личного компьютера AUTH_MODE=local: вход и роли пользователя отсутствуют; все локальные документы доступны владельцу. API/UI публикуются только на loopback, запросы с чужими Host/Origin отклоняются. Debug включается серверной настройкой. Опциональный token-режим сохраняет actors/grants для отдельного сценария; публичный Demo требует обезличенного корпуса.

REQ-EXT-57-01. Upload проверяет magic bytes, extension, размер и ограничения DOCX ZIP: число entries и суммарный uncompressed size. Внешняя загрузка использует allowlist, запрет private/loopback/link-local IP после DNS resolution и на каждом redirect, timeout и download limit. Не исполнять macros, embedded scripts и внешние ссылки документов.

REQ-EXT-57-02. Документные инструкции считаются данными, а не командами модели. LLM не получает инструментов удаления, сети или запуска кода. UI экранирует source text; Ответ на языке обращения и цитаты на иврите показываются в отдельных bidi containers без изменения текста источника.

REQ-COST-01. Сохранять usage по каждому provider call и агрегировать query/job/day; token prices имеют provider/model, effective_date и источник. Учитывать перевод запроса, локальные ресурсы embeddings, rewrite, reranker API, answer и comparison, а не только итоговый ответ. Оценка по тарифу не заменяет invoice.

REQ-EXT-57-03. До тематического сравнения учитывать перевод, оба evidence contexts, max input/output, retries и цену в TOPIC_COMPARE_COST_LIMIT; все provider calls входят в один бюджет запроса. При достижении лимита прекратить следующие вызовы и вернуть BUDGET_EXCEEDED без неподтверждённого сравнения. Повтор не обнуляет уже понесённую стоимость.

REQ-EXT-57-04. Бесплатные токены/квоты аккаунта — переменная скидка, не основа гарантированной себестоимости. Не включать передачу данных для обучения автоматически. Внешние вызовы выполняются только с выбранной пользователем конфигурацией и допустимым корпусом.

REQ-EXT-57-05. Backup покрывает PostgreSQL, raw files и конфигурацию; Qdrant backup либо проверенная процедура rebuild. Restore тестируется до приёмки; восстановленные fingerprints должны совпадать с активными generations.
